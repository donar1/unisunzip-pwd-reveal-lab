## 一、你要的三件事，怎么实现的

| 你的需求 | 实现方式 |
|---|---|
| **显示**（圆点变明文） | 接管 `QLineEdit::setEchoMode`，把下传的 echo 模式强制改为 `0 = Normal` |
| **复制** | 模式变 Normal 后就是普通输入框，可直接 `Ctrl+C` / 选中右键复制 |
| **统计** | 接管 `QLineEdit::setText`，凡是写进"密码框"的文本都追加落盘，再用台账工具汇总 |

程序里"查找密码"的结果是按 `PasswordEchoOnEdit`（值 3）显示的 —— 有焦点时明文、失焦时变圆点，
所以平时看到的就是一圈圆点。

## 二、技术方案（为什么能一次做对）

**没有源码，所以走「二进制补丁 + 代码洞穴」路线**：

1. 在 exe 尾部新增一个节 `.unispw`（VA `0x7f000`），里面放两段注入代码；
2. 把 exe 里 11 处调用点原地改写，跳进洞穴：
   - `QLineEdit::setEchoMode` —— 全 exe 只被调用 1 处（rva `0x1e89c`，下传的正是 `3`）
   - `QLineEdit::setText` —— 10 处
3. 洞穴代码全部用 RIP/ImageBase 相对寻址 → **兼容 ASLR**，无需改重定位表；
4. 日志路径运行时用 `GetTempPathW()` 取 `%TEMP%`，不写死（该程序是 `asInvoker`，
   而 `Program Files` 对普通用户只读，写死必然失败）。

**日志格式**（`%TEMP%\UNISUnzip_pwd_log.txt`）：

```
01DA3F8C12345678<TAB>TestPass123<CRLF>
└─ 16位十六进制 FILETIME(UTC)      └─ 密码（UTF-8 明文）
```

## 三、上一轮遗留产物的 5 个坑（都已修掉）

工作区里原有的 `patch_unis.py` / `UnISUnzip.exe.patched_tmp` 是上一轮的未完成品，**直接落地会崩**。
实测定位到 5 处缺陷：

| # | 缺陷 | 后果 | v2 修法 |
|---|---|---|---|
| 1 | 把 `FF 15 disp32`（间接调用）的 disp 指向代码区 | 执行时拿代码字节当函数指针 → **必崩** | 改为等长的 `E8 rel32 + 0x90` 直接调用 |
| 2 | 只判断 `echo mode == 2` | 程序实际传的是 `3`，**即使不崩也毫无效果** | 改为 `mode != 0` 一律强制 0 |
| 3 | `sub rsp` 后 `rsp%16==8` 就调外部函数 | 违反 Win64 ABI，Qt 里用 SSE 对齐指令时崩溃 | 每个函数入口精算 16 字节对齐 |
| 4 | 日志写死在 `C:\Program Files (x86)\UNISUnzip\` | 无写权限，`CreateFileW` 必定 `ACCESS_DENIED` | 运行时 `GetTempPathW` 取 `%TEMP%` |
| 5 | `QString::utf16` 从 `Qt5Widgets.dll` 里查 | 该符号在 `Qt5Core.dll` → 永远返回 NULL | 改为从 `Qt5Core.dll` 解析 |

> 另外两个工具链级坑：keystone 的 Intel 语法把**裸数字当十六进制**（`and eax, 15` → `and eax, 0x15`）；
> keystone 0.9.2 遇到 asm 里的 `;` 注释会**直接段错误**（进程消失、无任何报错）。

## 附录 A、「点查找密码就闪退」复盘（2026-09-21，已修复）

**现象**：点「查找密码」→ 程序瞬间消失，无任何提示。

**关键取证**：Windows 应用日志近 4 天**没有任何 UNISUnzip 崩溃记录**，
WER `ReportArchive` 的 149 条报告里也没有一条，`CrashDumps` 里同样没有。
—— 一条记录都没有，说明不是普通的内存越界崩溃（那会留下 WER 报告）。

**根因：补丁破坏了 Win64 非易失寄存器 RDI / RSI。**

排查链条（每一步都留下了证据文件）：

| 步骤 | 检查内容 | 结果 |
|---|---|---|
| 1 | 符号名 `?utf16@QString@@QEBAPEBGXZ` 是否真在 Qt5Core.dll 导出表 | **存在**（`check_syms.log`），排除 |
| 2 | 6 个硬编码常量对应的 IAT 槽 RVA 是否真的是那些函数 | **6/6 全对**（`iat_map.log`），排除 |
| 3 | 逐行重审洞穴汇编 | **发现 caveB 只保存 RBX/RBP/R12-R15，漏了 RDI/RSI** |
| 4 | 新增哨兵回归测试验证（`emu_nonvol.py`） | **FAIL**：RDI 被改成 `0x140080091`、RSI 被改成 `0x140080796` |
| 5 | 静态数据流复核调用点（`callsite_flow.py`） | **8/11 个调用点返回后会读 RDI/RSI**，含 0x1e882（弹窗构造，紧邻 setEchoMode 处 0x1e89c） |

**完整因果链**：

```
点「查找密码」→ 弹窗构造 → 调 QLineEdit::setText（被 caveB 接管）
   → caveB 拿 RDI 当缓冲区指针、拿 RSI 当常量指针，却没保存
   → 返回后调用方执行 mov rdx, rdi，拿到的是垃圾指针
   → 立刻访问违例 → 闪退
```

> Win64 ABI 规定 **RBX, RBP, RDI, RSI, RSP, R12-R15** 必须由被调函数保存并恢复。
> caveB 是"冒充 setText"的，调用方完全有权在返回后继续用 RDI/RSI。

**为什么之前的两轮验证没抓到**：上一版仿真器只断言了「栈 16 字节对齐」和业务逻辑，
**没有检查寄存器保留性**——ABI 的另一半根本没人看。这次补了 `emu_nonvol.py`
（给 8 个非易失寄存器写哨兵，跑完逐一比对）。

**修法**：caveB 与 resolve_all 各增加 `push rdi / push rsi`（push 数从 6→8、3→5，
`sub rsp` 的对齐刚好不变，已重算确认）。修复后：

- `emu_nonvol.log` → **PASS**（4 条路径非易失寄存器全部保留、栈对齐 0 违规）
- `emu_v2.log` → **PASS**（业务逻辑与日志格式不变）
- `verify_v2.log` → **PASS**（仍只改 73 字节，11 个调用点重定向正确）
- `verify_load_build.log` / `verify_load_green.log` → **PASS**（依赖闭包 0 缺失）

**火绒嫌疑已被实测证伪**：修复后在**火绒 HipsDaemon 全程运行**的状态下实测通过——
补丁在 HIPS 环境下照常工作，先前"被安全软件静默结束进程"的推断不成立。
（保留一条提醒：本补丁的行为特征——截获输入框明文并写文件——与窃密木马同构，
不排除将来火绒规则更新后误拦；若要长期使用，建议在火绒里给该 exe 加白名单。）

**为什么要把台账从 Python 版改成网页版**：原版 `pwd_ledger.py` 依赖本机 Python 环境，
换台机器就打不开 —— 这是对外分享最大的障碍。新版**零依赖**：接收方什么都不用装。

**台账的两条载入通道**：

1. 双击 `2-打开密码台账.bat` —— 脚本读 `%TEMP%\UNISUnzip_pwd_log.txt`，
   生成 `pwd_data.js`，再打开网页，数据直接在里面。
2. 直接把日志文件**拖进网页**（或点右上「选择日志文件」）—— 不依赖任何脚本，永远可用。

**两个技术要点（这次踩出来的）**：

- **不能靠网页自己去读本地文件**。浏览器把 `file://` 页面的 `fetch` / `XHR` 当跨域拦死，
  但 `<script src="本地.js">` 是允许的 —— 所以走「脚本把数据写成 `pwd_data.js`，
  网页用 `<script>` 加载」这条通道。
- **数据文件必须做成纯 ASCII**。脚本把日志里所有非 ASCII 字符转义成 `\uXXXX` 再落盘，
  彻底绕开「谁按什么编码读」这类问题。实测生成的 `pwd_data.js` 无一个字节 > 127，
